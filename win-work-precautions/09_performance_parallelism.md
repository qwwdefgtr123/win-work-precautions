# 09 性能与并行（Performance & Parallelism）

> 优先级 🟡 场景触发。加载条件：计算密集型任务、大批量文件处理、并行调度、考虑使用 GPU。
> 本文给的是**决策方法与基准测试流程**，不给具体数值结论——数值必须现场测。

## 复用优先于重探

- If 目标机器上已有实测档案（硬件画像、推荐并发数、基准结果），Then 直接读取复用，
  不要重新探测硬件或凭直觉设并发度；档案缺失、机型变更或负载类型不同则重测。
- 重测后把结果写回档案（含测试日期、负载类型、样本规模），供后续会话使用。

## 并发决策流程（必须实测得出）

1. 用**同一份小样本**跑阶梯基准：并发度依次取 1 / 2 / 物理核数 / 逻辑处理器数（/ 若干中间点），
   记录总耗时与吞吐。冷热交替、多轮取中位，抵消系统缓存带来的偏差。
2. 取"吞吐不再提升或开始下降"之前的最后一个并发度作为 CPU 密集上限。
   **不要默认按逻辑处理器数开满**：混合性能/能效核的 CPU 开满时，慢核会拖累整体，
   吞吐反而明显低于按物理大核数并发（实测可低约四分之一）。
3. I/O 密集（网络、多子进程等待）可给更高并发（逻辑核数的 2～4 倍起步，仍按基准收敛）。
4. 重磁盘 I/O 的外部命令并发 ≤ 8；全盘目录遍历属单盘 IOPS 瓶颈，多线程枚举单卷通常无收益。
5. If 单个任务耗时 < ~0.3s，Then 不要用多进程（Windows 进程创建开销约 0.1～0.2s，收益为负），
   改批量合并或线程池。
6. CPU 密集型计算不要靠线程绕过解释器全局锁（增益近 1.0），要多进程；
   I/O 型任务用线程更省。
7. 内存受限机型（核显共享主存、总内存 ≤ 16GB）重任务预留约 20% 余量；
   不要同时叠加大内核 GPU 任务与满线程 CPU 任务——主存带宽会互相争抢。

## GPU 使用判据

- 计算密度 = 运算次数 / 搬运字节数。If 密度不超过约 20 运算/字节，Then 用 CPU：
  逐元素运算、向量加、哈希、压缩类受带宽限制，核显上 GPU 往往慢一个数量级。
- 适合 GPU 的是高密度批量运算：矩阵乘、卷积、大规模向量相似度检索（核显也能拿到数量级加速）。
- 集成 GPU 上跑 LLM 只适合小参数量级模型，且使用官方推理框架，不要手写内核或指望大模型可用。
- If 目标机器无独显，Then 明确告知用户性能天花板，不要为"上 GPU"设计复杂工程。
- 任何"该不该上 GPU"的争议用同一份数据的基准对比解决（含数据传输开销的端到端耗时才算数）。

## 索引/缓存加速的价值判定

- If 计划引入"元表/变更日志/预建索引"来加速查找，Then 先做与直接遍历的端到端对比：
  变更日志只保留近期记录（父链滚出后无法重建完整路径），
  批量枚举 API 每轮需重定位 B+ 树，吞吐可能远低于朴素遍历。
- 对比必须同盘同范围、交替顺序、多轮取中位；变更日志类是整卷枚举，不能与子树遍历直接比。
- 只有在数据规模、查询频次、可容忍的陈旧度三项都成立时才值得建索引；否则直接遍历是最优解。

## 测速与基准的通用纪律

- 只测目标阶段：给被测程序提供"提前空转退出"的参数（如极大过滤阈值）隔离出待测阶段耗时。
- 解析程序自打的计时行时，注意其输出编码与标点全半角，别用易失真的正则。
- 并发拉满的检索（如大范围递归 grep 大型混淆产物）会耗尽 CPU 并拖死交互终端：
  探索类任务限定范围或走子代理。
