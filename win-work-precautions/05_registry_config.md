# 05 注册表与系统配置（Registry & Configuration）

> 优先级 🟡 场景触发。加载条件：要读写注册表、改系统/用户配置、做系统集成
> （右键菜单、协议处理器、开机自启、Shell 扩展、策略键）。

## 前置探测（改动前必做，全部只读）

1. **令牌形态**：当前进程是否提权、提权后 HKCU 指向哪个账户的配置单元
   （提权会话里的"当前用户"通常不是你操作的那个用户，见下文"配置单元陷阱"）。
2. **视图**：目标键在 64 位视图还是 `WOW6432Node`（32 位）视图；同名键是否两侧都存在。
3. **键存在性与原值**：目标键是否已存在、现有值的**类型**（`REG_SZ`/`REG_EXPAND_SZ`/`REG_MULTI_SZ`/`REG_DWORD`）
   与原始数据。**先读到原值再谈修改**，读不到就不要写。
4. **写入通道权限**：能否写 HKLM（通常需提权）与当前用户配置单元；组策略/安全软件是否对该键设了保护或会还原。
5. **影响面**：该键被哪些组件消费、改动是否需要重启/重新登录/广播通知才生效。
6. **可回滚性**：导出通道是否可用（`reg export` 与实际 CLI 工具存在性先验证），备份落盘位置是否可写。

探测失败的项记"未知"并降级为只读；**权限不足时不要用"命令返回 0"判定写入成功**，必须回读。

## 读写前

- **枚举含中文的键值一律用原生注册表 API（如 Python `winreg`）**，不要走 PowerShell 内联或
  批处理：编码链路会把中文键名/值变坏并**静默返回空集**（不报错，最难发现）。
- 查询用 `Get-ItemProperty` / `Get-CimInstance` 等结构化接口；在受限令牌下传统查询命令
  可能报"拒绝访问"或语法错，那不代表信息不可得，改接口或提权。
- 键的路径写法：`WOW6432Node` 视图与 64 位视图是两份数据，读写 32 位软件配置时需显式选择视图；
  同名键两份都存在时，人为改动常只在一侧，判断"被谁改的"要两侧都查。

## 修改前必做

1. **导出备份**：`reg export "<完整键路径>" <文件>.reg /y`，备份落在工作目录并记录键路径。
2. **记录原类型与原值**：写回时必须沿用原 `REG_` 类型。含环境变量引用的值
   （如 `%USERPROFILE%\...`）**必须保持 `REG_EXPAND_SZ`**，写成 `REG_SZ` 会导致变量不展开、
   路径失效（典型：改了用户 Shell Folders 后桌面/文档指向错误）。
3. **配置单元陷阱**：提权会话里的"当前用户"（HKCU）指向**提权账户**的配置单元，
   不是交互用户的。要读写交互用户配置，用 `HKU\<用户SID>\...` 显式路径。
   同理，删除用户级残留时别在提权进程里用 HKCU 相对路径。
4. 若目标是"用户登录前就要生效"的项，写 HKLM 而非 HKCU（后者需登录后才加载）。

## API 与工具的具体坑

- `QueryValueEx` 返回 `(value, type)` 二元组，按三元组解包会抛 `ValueError`。
- 删除默认值必须传空串 `''`，传 `None` 无效。
- 删除带子键的键返回 error 5（看起来像权限问题），实为**必须递归先删子键**。
- 注册表 ACL **不支持继承标志**：构造访问规则要用不带继承标志的重载，传 `ContainerInherit` 直接抛异常。
- 读取键的"最后写入时间"在近代 Windows 上不可得（相应查询接口已移除）。
  要定"配置何时被改"，改用**目标目录自身创建时间 + 应用自己记录的时间戳值**交叉推断。

## 权限被拒时的选型法则（重要）

- 通用观察：在受管控的执行环境里，**新建键 + 新值**通常被放行，而**修改/删除已存在的系统键值**
  常被安全策略拒绝（即使跳出沙箱、即使提权）。
- → 做系统集成需求时，**优先设计成"纯新增"方案**：
  `HKCU\Software\Classes\<类型>\shell\<名称>` 系列右键菜单（文件/文件夹/驱动器三类）、
  自定义协议处理器、HKCU 下的 per-user 配置。
  卸载 = 删掉自己新建的键（属于"删新建"，不受限）。
  命令值中参数占位符必须引号包住（`"<exe路径>" "%1"`），否则含空格路径会断。
- If 必须改存量系统值且被拒，Then 不要堆叠提权尝试（换通道也一样），
  把可双击运行的脚本连同说明交付给用户手工执行，这通常是最快路径。
- **判定"写入失败是不是策略拦截"：做对照实验**——同一会话里"新建键写新值"成功、
  "改已有值"失败，即可定性为策略层，而非权限或杀软。

## 修改后

- **读回校验**：重新读取值与类型，确认与预期一致。
- 需要生效于 Shell 的改动（桌面图标、文件夹指向、自启项）：仅广播变更通知不够，
  常需重启 Explorer 进程（先杀再起，避免 shell 不自愈）。重启前告知用户会关闭几个资源管理器窗口。
- 电源/网卡/服务类设置：**改后必须读回当前值**（`powercfg /query`、`Get-Service` 等），
  且部分驱动设置需禁用/启用设备或重启才加载，别把"下次重启才生效"误判为失败。
  改电源类设置一律用**别名**（`SCHEME_CURRENT`、`SUB_*` 等）而非硬编码 GUID
  ——OEM 方案常使用定制 GUID 后缀，喂标准 GUID 会报"设置不存在"并在静默继续策略下白改。
- If 该配置可能被第三方软件改回（DNS、代理、防火墙、启动项、更新开关），Then 写"预期基线"
  并安排只读巡检复核，而不是反复手工改回。

## 桌面图标与命名空间条目

- 系统命名空间类桌面图标（"此电脑""回收站"及被第三方挂载的条目）不落地成 `.lnk`，
  按文件扫桌面永远找不到；用 Shell 枚举桌面可见项来判定存在与否。
- 这类图标可能由 `Explorer\Desktop\NameSpace\{GUID}` 挂载强制显示，此时
  "隐藏桌面图标"的策略键完全无效——正确处置是备份后删掉该 NameSpace 子键。
- 判"某系统图标是否被第三方劫持"要四项齐查：CLSID 的 Open\Command 指向、
  HKCU 是否有同名 CLSID 覆盖副本、目标 exe 的 IFEO `Debugger` 值、文件数字签名。
