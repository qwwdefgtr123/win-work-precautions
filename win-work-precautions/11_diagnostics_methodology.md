# 11 故障诊断与取证方法论（Diagnostics & Forensics）

> 优先级 🟢 扩展参考。加载条件：需要归因（"为什么坏了/为什么不见了"）、
> 验证系统组件完整性、做删除溯源、或判断某项"不可用"结论是否成立。

## 核心原则

1. **先分层分类，再取证**。互斥的原因不能互相解释，混在一起必然得出错误结论。
   典型分层：硬件/固件层 → 枚举与驱动装载层 → 分区层 → 卷层 → 文件系统层 → 内容层 → 应用层。
   每层给一条**只读判据**，逐层排除；先确认上层正常，下层结论才有意义。
2. **只读优先，判据先于结论**：任何复位/修复类命令的"成功回执"都不是判据，
   故障征候本身才是（例：回执"已成功重启设备"但错误码依旧 → 故障在硬件层，软复位无解，别反复试）。
3. **交叉验证**：同一事实至少两个独立来源一致才定案（不同工具口径互证、
   时间戳链条互相闭合）。若只有单源，结论降级为"待证"。
4. **归因要落证据**：数据出来前不给猜测定性；点名"谁做的"必须有句柄、日志、时间线级别的证据链。
5. **处置按从轻到重排序，逐级试**：重连 → 优雅停止 → 强制停止 → 手工修复。
   跳过前几级直接强杀/强改，常把可恢复问题变成数据损失。
6. **互斥成因必须分别处置**，别指望一招通杀（同一现象可能由三类独立原因造成，
   修好其中一类不会让另一类消失）。

## 对照实验设计（可复用的四组）

- **策略拦截 vs 权限**：同一会话里"新建键 + 新值"与"修改已存在的系统值"各写一次。
  前者成功后者失败 → 策略层；两者都失败 → 令牌层（回去提权）。
- **盘坏 vs 口坏 vs 系统坏**：用设备所在端口的历史成功记录反证端口可用；
  同一设备在 ≥2 个物理端口都失败 → 强力指向设备自身；
  同机近期成功枚举过同类设备 → 排除系统栈。
- **防护是否真在工作**：双载体交叉（脚本内容通道 vs 可执行文件落盘通道）+ 足够观察窗；
  单载体、短窗内的"无反应"不足以定"失明"。
- **性能瓶颈定位**：分阶段计时（解析 / 建连 / 安全握手 / 首字节 / 总耗时），
  一眼看出慢在哪一段；冷热交替多轮取中位，避免缓存制造的假象。

## 系统组件完整性判读

- **不要从"某文件不在预期路径"直接推"文件被删"**。正确顺序：
  1. 查该服务/组件**实际引用的模块路径**（服务参数里指向的可能完全是另一个文件名）。
  2. 查组件包里实际登记的文件清单（组件存储才是权威：清单里没有，就该不存在）。
  3. 查同功能的多形态变体（同一组件常有针对不同子系统/架构的后缀变体，通常只需其一）。
  4. 以上都排除，才轮到怀疑被删，且需要日志级佐证（损坏日志中明确的"文件未找到"错误码 +
     同目录其他文件正常 + 修复工具无法还原 + 组件清单确实登记该文件）。
- 修复类工具报"还原成功"但文件仍"缺失" → 结论是"本来就不该有"，不是"修不回来"。
- 服务报"拒绝访问"类错误的排查顺序：先测 `ImagePath` 指向的文件是否存在 → 服务注册表项
  （Start/Type/ObjectName/ImagePath）→ ACL 与自定义安全值 → 最后才怀疑策略。
  **不要默认怪组策略。**
- 幽灵服务/启动项扫描（指向不存在文件的条目）三条必做归一化：
  去内核路径前缀、展开环境变量、**剥离命令行参数**（否则带参数的路径全被误判缺失）。
  启动项判读要宽松（宁漏报不误报），服务判读可严格。
- 判定系统运行状态时，注意第三方安全组件会把内核对象锁死（文件、注册表键、句柄），
  "删不掉/改不动"可能是拦截而非损坏；同时注意某些异常状态是正常设计
  （如按需加载的驱动停在停止态、一次性注册器不在运行态）。
- 若怀疑某项调优被回滚：与记录基线比对（路由跃点、TCP 参数、服务启动类型、DNS），
  差异既可能来自第三方软件，也可能来自系统更新——只报事实，不猜元凶。

## 磁盘、卷与设备判读

- 报"某文件/容器正被系统在打开"或共享冲突：先确认是否被挂载为虚拟磁盘
  （枚举磁盘类设备看是否存在虚拟磁盘型号），再停相关写保护/快照类服务；
  提权后仍查不到句柄却删不动 → 指向内核级拦截（走更早执行点或离线处理）。
- 卷"根目录空但属性显示已占用若干 MB"属正常：占用是文件系统元数据（主文件表、日志、位图），
  小容量卷上占比会显得很大。判"制作/写入是否成功"用两条硬证据：
  已用空间是否达到内容量级、以及系统卷信息目录的创建时间（= 格式化时刻）与其后是否有任何写入。
- 卷标与图标不可信：判内容必须实际枚举统计；启动菜单无条目（无引导文件）与
  设备列表看不到（固件/硬件问题）是两件事，别互相解释。
- 修复虚拟磁盘/容器类文件前，先做三步只读定性（配置指向、描述符存在性、官方校验工具的输出），
  **修复类操作必须在实例停止后执行**——运行中执行会争锁并输出误导性的"已修复"文案。
- 判断"某环境不识别设备"要分类：设备本体 / 盘内内容 / 该环境组件缺失。
  宿主机能完整读写即可排除本体，之后只在后两类找。

## 删除溯源与取证（"文件不见了"）

三源各司其职，交叉使用：

- **卷影副本（VSS）**：定"文件是谁、内容是什么、最后存在于哪个快照之间"。
  列举快照后按创建时间映射，用设备路径直接访问快照内容。
  注意：部分 Shell 接口打不开快照设备路径（会静默返回 false），必须用原生文件系统 API
  （提权下目录枚举/打开）读取；恢复内容按字节原样写回，不重新编码。
- **变更日志（USN journal）**：定"精确删除时刻 + 是否经过回收站"。
  记录只有文件名没有完整路径，需靠父索引链反解；用文件索引查询接口拿到目标目录的真实 FRN
  （注意返回值高位补零，需按低 16 位十六进制归一），再筛"父 ID == 该 FRN"的直属子项事件。
  无"改名到回收站"类记录 = 未进回收站（永久删/程序删，回收站还原救不了）。
  同一秒内成批的删除对是"清空回收站"的特征签名。
  **窗口极短**（日志容量有限、重启即截断），要趁早采集。
  解析中文系统输出的坑：表头不在第一行（前面有摘要块）、列序与英文文档不同、
  列名可能含空格（写错会静默拿到空值）、时间戳分隔符显示层与字节层不一致（用字节十六进制核对）。
- **回收站元数据文件（`$I`）**：定"原始完整路径 + 删除时刻"（`$R` 存在与否说明数据是否还在）。
  布局：版本、大小、FILETIME 删除时刻、路径长度、UTF-16LE 原始路径。
  FILETIME 换算必须显式转本地时区，否则会把时间算错一个时区差并导致因果判断颠倒。
- 系统"对象删除审计"默认常未开启，且日志轮转很快 —— 事件日志这条路走不通时要早换路，
  别在空结果上耗轮次。
- 取证通用坑：注册表键无写入时间戳可用；同卷移动保留原创建时间（判断"何时搬家"只看目录自身）；
  混合编码输出不要整份按 UTF-16 解（见 `02`）。

## 浏览器与桌面自动化诊断

- 语义优先于坐标：桌面自动化优先用控件树（可读文本、可定位元素），OCR/坐标作兜底；
  点击走控件模式（Invoke/Toggle）再兜底消息投递，**不移动全局光标、不劫持键鼠**。
- If 需要接管用户真实浏览器会话，Then 记住：默认配置目录上通常禁止开调试端口；
  复制配置副本到 ASCII 路径再启动是可行路径，且复制前必须确认浏览器进程已归零（否则文件被锁）。
  登录态与浏览器实例指纹可能绑定，复制 cookie 到新实例会被判异常会话而降级返回内容。
- 合成事件有边界：部分页面忽略非可信点击、脚本填值不触发逐键自动补全；
  如实报告"无可见变化"并回读目标属性（如链接绝对地址）交给人，不要伪造成功。
- 收尾必须回收自己启动的浏览器实例（按专属数据目录精确匹配命令行回收），
  不误伤用户日常浏览器进程；验证方式是自己起的实例计数归零。
- 高危动作（点击/输入）在未获授权时返回"需人工授权"而非硬执行；提供急停与预演（dry-run）能力；
  失败如实上报。

## 产出规范

- 诊断结论必须附证据链：引用具体文件路径 + 命令输出落盘件 + 时间点，能逐条复核。
- 结论分三级写：**已证实**（多源一致）/ **高度疑似**（单源但反证已排除）/ **未知**（缺证据）。
  禁止把"未知"写成"没有问题"。
