# 08 网络、代理与下载（Network & Proxy）

> 优先级 🟡 场景触发。加载条件：网络不通/慢、下载失败、网页异常、代理类故障、
> 需要判断"是环境问题还是目标问题"。

## 前置探测（下结论前必做，全部只读）

网络问题的误判几乎都来自"跳过了某一层"。本节的探测必须**先于**任何修复动作，且结果要落盘成
可对比的记录（时间点 + 现象 + 命令）。

1. **三个互不相通的代理层各自是什么状态**：系统/浏览器读的注册表代理设置、命令行工具读的
   `HTTP_PROXY`/`HTTPS_PROXY` 环境变量、系统组件读的 `netsh winhttp` 代理。
   **三者不一致是常态**，只查一层就断言"没有代理"是常见误判。
2. **解析层**：解析器实际返回的地址（不是缓存里的），是否被 hosts 覆盖，是否回环/私有地址。
3. **链路层**：TCP 能否建连、TLS 握手能否完成——**"域名解析成功但连接失败"和"解析就失败"是两类故障**，
   处理方向完全不同，不要混在一起查。
4. **出口层**：是否存在 VPN/虚拟网卡/多默认网关导致选路错误。
5. **工具自身**：所用的下载/请求工具是否**读代理**（不同工具读的环境变量与配置文件不同）、
   是否校验证书吊销（部分环境会因此直接失败而非降级）。
6. **对照基线**：至少准备一个"同一目标直连 vs 走代理"和一个"本机回环 vs 外网"的对照，
   没有对照就无法归因。

探测阶段不修改任何代理/DNS/hosts 配置。确需临时变更时，先记录原值，收尾必须恢复原值并回读确认。

## 先做状态面采集（全部只读）

采集并记录：hosts 中生效的非注释行、接口与 DNS 配置、路由表与接口跃点、
当前系统代理设置（开关 + 指向 + 绕过表）、代理类进程、无线接口实况（频段/信道/协商速率/信号）、
TCP 全局参数、本机监听端口及其属主进程。
注意：无线网卡的高级属性与电源管理接口在部分驱动上即使提权也返回空，需改读设备类注册表子键；
协商速率与实际吞吐口径不同，不要用其中一个否定另一个。

## 分诊顺序（决定后面查什么）

1. **先判"是不是代理的锅"**：同一目标分别用 `--noproxy '*'` 直连与走代理计时对比。
   直连快、代理慢/挂起 → 问题在代理链路，别去查 DNS 或应用。
2. **再判物理层与频段**：信号强度、协商速率、当前是否挂在低性能频段。
   频段"信号最强"不等于"体验最佳"——以实测速率与延迟尖峰为准，并同时看丢包。
3. **DNS 质量必须实测**：系统解析接口与 `ipconfig` 会被本地缓存骗成 0ms；
   要测真实 RTT 需构造原生 UDP/53 查询并按查询 ID 匹配响应。
   **境外或被污染 DNS 的代价远不止解析慢**：它会把就近服务的域名解析到海外/劣质 CDN 节点，
   连带把 TCP 与 TLS 阶段全拖崩。换用就近 DNS 后整链路可能数量级改善。
   改 DNS 属需提权的配置变更，须按 `03` 备份原值、读回校验，并预期第三方软件会改回。
4. **网络接口选路**：存在虚拟机网卡/VPN 网卡时检查接口跃点，异常跃点会让流量走错出口。
5. **本机回环也慢 → 查内核过滤**：If `127.0.0.1` 建连就有固定毫秒级开销，Then
   这是内核过滤平台（WFP）挂载的第三方模块（网络监控/防劫持/TLS 深检）造成的每连接固定成本，
   与"应用/代理"无关，缓解只能减少连接数或经用户同意调整该模块。
   文件系统类过滤器不在网络路径上，不要用过滤器枚举命令去解释网络延迟。
6. **TLS 首轮慢是普遍现象**（证书链/CRL 拉取）：同一目标至少测两次再下结论。

## 三类阻断的判别法（DNS 污染 / SNI 阻断 / IP 封锁）

- 手段：把"域名"与"真实 IP"分离测试。真实 IP 从外部解析服务获取（避免本地污染输入），
  再用强制指定 IP 的方式直连目标端口。
- 判读：用 DNS 给的地址超时、但换某个真实 IP 秒连 → **DNS 污染**（钉住可用 IP 即可缓解）；
  TCP 能连上但 TLS 握手立即失败 → **SNI 阻断**（换通道，不是配置问题）；
  TCP 完全连不上 → **IP 封锁**。
- 同域名不同 IP 命运不同是常态：IP 白名单会漂移，需定期重测，不要把某次的最优解固化。
- **代理端解析必须显式启用**（SOCKS 下让代理做 DNS），否则本地污染照样让请求失败；
  代理端口会随重连漂移：读配置必须现场读注册表与监听端口，
  浏览器/脚本记死旧端口就会表现为"连不上"。多代理客户端共存时会互相抢占系统代理开关，
  最坑的是"幽灵代理"——代理已退出但开关仍指向无监听的端口，表现为全站连不上；
  判据：代理开关开启且指向某端口，而该端口无监听。分层连通测试可区分
  "代理活着但无出口"（境内站 200、境外站 000）与"代理口已死"（连境内站都不通）。
- 交付给用户的浏览器入口应复用其日常浏览器配置以保留登录态（用户长期偏好），
  只有做隔离测试时才用独立 profile。

## 网页"打不开/加载不出来"的浏览器侧判据

- If 页面静态资源全 200 但 XHR/fetch 长期 pending、页面永远骨架屏 →
  是系统代理对 API 通路的劣化，而非站点或浏览器故障。
  处置：临时关闭系统代理并广播刷新（Chromium 内核热感知，无需重启），完成后恢复原值。
- If 站点强依赖 WebSocket 而代理不透传该协议 → 表现为"某些站连不上、其他站正常"。
  判别：同代理下多家站点首页都通、只有依赖长连接的那家握手挂起；解法改用透明隧道模式
  （SOCKS 入口或整机隧道），不要改站点侧配置。
- 代理会重置绕过表：浏览器代理例外清单常被代理客户端清空，需复核重设。

## 下载取源（受限网络下的可用路径）

- 找源顺序：官方 CDN/就近镜像 → 国内镜像站 → 代码托管平台及其可用加速前缀 →
  由他人转存的镜像仓库（最后手段，且必须校验）。
- **加速代理前缀只服务于其声明覆盖的域名**，套任意站点会返回错误页；
  因此每一次下载后都按上面的"类型 + 字节数"双校验。
- 面向脚本可访问的下载渠道优先；需要 JS 渲染或人机验证的站点不作为自动化目标（不硬闯）。
- 部分下载器只支持 HTTP 多线程，不支持对等网络协议——选型时先确认协议支持，
  别把工具能力当环境事实。

## hosts 与出站阻断

- 需要稳定封域时优先防火墙按程序路径的出站阻断（比 hosts 耐篡改）；
  hosts 修改保留注释与用户既有条目，只增删自己新增的行，读取用带 BOM 兼容的编码。
- **不要为了省事改动用户既有的 hosts 条目、代理客户端配置或网络基线**；
  需要固定端口之类的诉求用旁路方案（本机端口转发）实现，不动原配置。
- 封域前先按用途与 IP 段把"服务更新通道"和"组件分发通道"分开验证：
  把整个厂商域名族一并保留会留下回补通道；把安全更新的域封掉则自损防护。
  **没有证据的域名不写进屏蔽表**（域名出处必须来自配置文件/清单/字符串提取，不是猜测）。
- 防火墙规则的批量地址参数有分隔符限制，多地址写成多条单地址规则，
  否则报"IP 地址无效"。

## 自动化访问外部站点（合规红线）

- 默认只交付合规方案：真实浏览器 + 用户本人单账号登录态 + 遵守 robots + 限速 + 敏感字段脱敏 +
  命中验证码/登录墙/风控时立即暂停并回报。
- **拒绝**指纹伪造、TLS 指纹伪装、验证码识别绕过、多账号凭证池轮询这类对抗性请求；
  已登录账号产生的写操作会改线上真实数据，操作前须确认目标内容。
