# 04 文件系统操作（File Operations）

> 优先级 🟡 场景触发。加载条件：要生成、扫描、统计、移动、清理、删除文件或目录，
> 或要做磁盘空间治理、应用迁移、快捷方式审计。
> 前置：先执行 `00` 的探测（磁盘剩余空间、是否存在链接点、目标路径实时状态）。

## 前置探测（生成 / 扫描 / 删除之前）

1. **目标路径的真实身份**：是否存在、是普通目录还是链接点（reparse point）、指向哪里。
   **链接点必须先解析再决定是否进入**，误跟一步就能把另一个卷的数据当真身处理。
2. **容量与配额**：目标卷剩余空间、是否有配额限制；写入量未知时先估算再落盘。
3. **占用者**：目标文件/目录是否被进程持有句柄（被锁则删除会失败或留下半截状态）。
4. **路径形态**：是否超长、是否含非 ASCII、是否需要 `\\?\` 前缀；短文件名（8.3）是否可用。
5. **删除的可恢复性**：目标卷是否支持回收站、是否网络盘/可移动介质（这些上面通常没有回收站）。
6. **批量规模**：待处理条目数量级，决定是否分批与是否先试跑。

扫描类任务在探测阶段**只读**：不移动、不改名、不删除，先出清单。

## 生成文件（写入侧）

- 执行文件生成任务前，先评估目标目录所在卷的剩余空间；空间紧张时优先使用临时目录或
  数据盘，避免污染系统盘核心路径（`C:\Windows`、`C:\Program Files`、用户配置单元根）。
- 中间产物与交付物分目录存放；交付物放入用户可见的输出目录，临时件放工作区，便于批量回收。
- If 目标文件已存在且要覆盖，Then 按 `03` 先备份原件。

## 扫描与统计（读侧）

- **扫描目录树时遇 reparse point（junction / symlink / mount point）只登记、不进入**：
  跟随链接会把另一卷或另一目录的体积错算进当前树，还会造成环路重复计数。
- 统计"删掉真能释放多少空间"必须对**硬链接去重**（按文件索引/句柄信息查询判定同一文件），
  否则系统组件区（如组件存储与系统目录互为硬链接）会显著虚高，实测单目录可虚高 2 倍以上。
- 遍历中"访问被拒"要计数并继续，不得致命退出；但**大差额必须提权重测**，
  否则受保护目录会静默漏计，导致总量判断错误。
- 全盘遍历以单盘 IOPS 为瓶颈：多线程枚举单卷通常无收益（先测小样本子树再决定是否并行，见 `09`）。
- If 计划用"索引/日志加速"（变更日志、元表直读类方案），Then 先实测吞吐再下结论：
  变更日志是流水账不是当前清单（父链滚出后路径重建成功率可为 0），
  元表枚举 API 可能比目录遍历慢一个数量级。默认解通常是直接遍历。

## 删除安全（核心章节）

**删除任何目录前，必须依次完成四项检查：**

1. **反查链接指向**：枚举"哪些路径是 reparse point 且其 Target 落在候选目录内"。
   目标机器上大量应用数据/运行时可能被链接重定向到他处，删掉"看似废弃"的目录
   等于连锁毁应用（浏览器配置、共享运行时、组件依赖）。有指向 → 先解除或改判，不下手。
2. **区分重复副本与唯一副本**：不能只做内容哈希比对，必须确认目录内每个主程序
   在他处仍有可运行的活副本；唯一副本所在目录不得当垃圾删。
3. **看实质不看名字**：版本目录 ≠ 安装残留（要看主程序与卸载器是否同级、主体 DLL 体积）；
   卷标、目录名、图标全部不可作为判定依据。判"空"要递归统计真实文件数。
4. **拿不准就问**：宁可漏清一个目录，不可误删一个数据目录。

**执行方式：**

- 按 `03` 走系统回收机制。If 单次删除条目过多（大目录树），Then 分批（每批 ≤ 100 项）
  逐项传入，并在删除前查占用者（句柄/端口反查 PID）；一次性整树操作常被安全软件的
  实时扫描或活句柄中断（表现为 abort）。
- **回收站有容量配额**：条目超过所在卷配额时系统会**直接物理删除**（不可还原、空间即时释放）。
  大项清理若希望留后手，必须先调大配额或改走分批小项；被点名保护的对象不进回收站流程。
- 清空回收站：部分环境下图形化清理命令提权后仍静默无效，需按用户 SID 子目录逐个处理，
  其他账户的受保护子项不强拆。
- **被锁文件的开机删除通道**：向会话管理器"待重命名/待删除"注册表队列
  （`Session Manager\PendingFileRenameOperations`，REG_MULTI_SZ）登记。规则：
  - 条目是 **(源, 目标) 成对**存储，目标为空串表示删除；**绝不能过滤空串**，
    配对错位会把"删除"变成"改名"，可能连锁改坏系统文件。
  - PowerShell 构造该多串值时会吞掉空串元素 → **必须用原生注册表 API（如 Python winreg）写入**，
    且写回后读回校验元素个数与末项为空串。
  - 只能删空目录，故登记顺序必须"文件 → 子目录 → 根目录"自底向上逐对登记。
  - 保留系统已有条目：先读现值，追加后整体写回。
  - 该队列可能被安全软件自愈过程盲写覆盖（lost update）：登记后保持静默（不杀其进程）、
    尽快重启，并在重启后复核。
- If 目标被链接/属性保护导致显示"找不到文件"，Then 用包含隐藏/系统项的枚举方式重查，
  勿误判为空目录。

## 长路径与特殊路径

- 超过传统长度上限的路径：用 `\\?\` 前缀（只认反斜杠、不做规范化）；
  短文件名（8.3）可能已被禁用，不可依赖它绕长度或中文问题。
- 深目录树清理后可能留下"每层各自入回收站"的同名碎片；判读删除记录时注意这一点。
- 带空格与括号的路径（`Program Files (x86)`）在命令行中必须整体加引号；
  写入注册表命令值时参数占位符也要引号包住。

## 快捷方式与特殊文件夹

- `.lnk` 的目标只能通过 COM（`WScript.Shell` 的 `CreateShortcut`）解析，直接读文件拿不到；
  `IconLocation` 是 `"path,index"` 字符串，按整串做前缀替换，不要当对象取属性。
- 桌面/文档等特殊文件夹路径必须用 API 获取（`[Environment]::GetFolderPath(...)`）：
  它们可能被云同步接管而重定向，`%USERPROFILE%` 下的同名本地目录可能根本不存在；
  实际显示内容还是"用户桌面 + 公共桌面"的合并，审计时两处都要看。
- 手工构造 `.lnk` 二进制结构不可取（PIDL/LinkInfo 不全时双击报找不到文件）；
  快捷方式创建优先用 COM 或交给用户系统菜单操作。
- 若清理后大量图标变白：真因通常是目标 exe 已不存在（图标从目标提取），不是缓存坏；
  修复 = 重装对应应用，或删除失效快捷方式后重启 Explorer 让其重建图标缓存。
- 安全软件可能专门拦截"跨目录移动 `.lnk`"（同目录改名与其他文件移动正常）。
  遇到该现象：`.lnk` 改用保真复制并保留源、事后按哈希逐项校验，不要与拦截硬拼。

## 应用与数据目录迁移

- 标准闭环：复制搬家（robocopy `/E /MOVE /XJ`）→ 原位建 junction 兜底旧路径
  → 批量改快捷方式指向新真实路径 → 验证应用可启动。
- 迁移前必须枚举所有指向源目录的链接点；迁移后不得产生新的悬空链接。
- 与系统深度集成的组件（浏览器内核与 WebView 运行时、共享运行库、安全软件本体、
  云同步客户端）不要迁移，会破坏更新与安全机制。
- 存储归属核对：浏览器缓存可能因链接重定向而实际占用他卷空间；
  顶层目录是真实目录 ≠ 其子目录不是链接，判"清 C 还是清 D"要逐个 profile 子目录查。
